## Why

Today the code generated by QAssistant lives only inside the platform: a QA
engineer reviews and approves a generated test, but moving that code into the
team's automated-test repository is a manual copy-paste, and QAssistant has no
record of whether the test actually landed in a repo. We want an MCP client
(Claude Code, or any MCP client) to read approved tests directly from
QAssistant, commit them to the team's Git repo using the client's own
credentials, and report the outcome back — closing the loop from capture to
integrated test without QAssistant ever holding Git credentials or pushing code
itself.

## What Changes

- **New MCP server** (`apps/mcp`, stdio transport) that acts as a client of the
  existing QAssistant REST API. It exposes tools to authenticate, list records,
  fetch a full record, list versions ready to integrate, and report integration
  results back.
- **Explicit auth tool**: an `authenticate(email, password, tenantId)` MCP tool
  exchanges credentials for an Identity Platform token; all subsequent tool
  calls act strictly within that tenant/user scope.
- **Integration status on generated tests** (**BREAKING** for the existing
  `integrated` boolean): the `generated_tests.integrated` flag becomes an
  `integrationStatus` enum (`not_ready` → `ready_to_integrate` → `integrated` /
  `failed_to_integrate`), plus a free-text `integrationRef` (commit or PR URL)
  and an integration error message. `integratedBy` / `integratedAt` are kept.
- **`ready_to_integrate` is automatic on approval**: approving a version
  (`reviewStatus = approved`) makes it the session's single integration
  candidate and replaces any previous candidate for that session.
- **One approved version per session (`superseded`)**: a new `superseded`
  review status is added. Approving a version marks every other version of the
  same session `superseded` (and demotes any still-pending candidate back to
  `not_ready`); a `superseded` version cannot be integrated. Approval can be
  switched at any time — approving another version (including a `superseded`
  one) makes it the active candidate and re-supersedes the rest. Versions
  already `integrated` / `failed_to_integrate` keep that integration record for
  history.
- **Client-driven, run-gated integration**: the MCP client adds the test to the
  target repo, **runs it**, and only on a **passing run** performs
  `git commit`/`push` with its own credentials and reports `integrated`. A
  failing run (or a test that cannot be run) is reported `failed_to_integrate`
  with the run output, and the failing test is not pushed to the main branch.
  When the client cannot locate the target test repo, it **asks the user** rather
  than guessing; if it stays unresolved, the version is reported
  `failed_to_integrate`. `integrated` therefore means "added AND the test passes";
  QAssistant itself never runs tests or pushes.
- **New dashboard column**: the records (sessions) list shows a derived
  integration status (`—` / `Ready to integrate` / `Integrated` / `Failed`)
  computed from the session's candidate version.
- **Dashboard integration is read-only**: the dashboard no longer offers an
  "Integrate" action. Integration is performed and reported exclusively by the
  MCP client (which owns the Git push); the dashboard only *displays* the
  integration status, reference, and error, plus a `superseded` badge on
  obsolete versions.

## Capabilities

### New Capabilities
- `mcp-integration`: an MCP server exposing QAssistant to MCP clients —
  credential-based authentication scoped to one tenant/user, read tools for
  records and code versions, a tool listing approved versions ready to
  integrate, and a tool to report integration outcome (success with repo
  reference, or failure with a message, including the "target repo not found"
  case).

### Modified Capabilities
- `knowledge-and-codegen`: the manual `integrated` boolean flag on a generated
  test becomes a four-state `integrationStatus` with a repo reference and error
  message; `ready_to_integrate` is reached automatically when a version is
  approved, and at most one version per session is the integration candidate.
  A new `superseded` review status enforces a single approved version per
  session: approving a version supersedes all others.
- `qa-dashboards`: the records list gains a derived integration-status column
  reflecting the session's candidate version. The dashboard exposes integration
  state read-only (no integrate action) and shows a `superseded` badge on
  obsolete versions; integration outcomes are reported only by the MCP client.

## Impact

- **New package**: `apps/mcp` (Node, MCP SDK, stdio transport, REST client of
  the QAssistant API). Added to the npm workspaces.
- **Schema / migration**: `generated_tests` — replace `integrated boolean` with
  `integration_status` (enum/text + check), add `integration_ref` and
  `integration_error`; new `INTEGRATION_STATUSES` enum in `packages/shared`.
  Data migration maps `integrated = true` → `integrated`, `false` → `not_ready`.
- **API**: a new endpoint (or extension of the existing review/integrate
  endpoint) to set integration status from a client; `ready_to_integrate`
  transition wired into the approval flow; dashboard sessions list/detail DTOs
  gain the derived integration field.
- **Shared DTOs**: `packages/shared` entities and dashboard DTOs updated for the
  new status, ref, and error fields.
- **Auth / security**: MCP server holds no long-lived secrets beyond what the
  client provides at `authenticate`; every tool call is tenant-scoped via RLS;
  QAssistant stores **no Git credentials** and never pushes to Git.

## Non-Goals (later phases)

- QAssistant pushing to Git itself, or holding any Git credentials.
- QAssistant creating or managing pull requests.
- QAssistant storing a per-project target-repo reference (the client locates the
  repo and asks the user when needed).
- Executing the generated tests or proving they pass in CI.
- A hosted/multi-user HTTP MCP transport (MVP is local stdio); HTTP can come
  later without changing the tool contract.

## Security, privacy, and data-retention assumptions

- **Tenant isolation**: all MCP reads/writes go through the authenticated user's
  token and existing row-level security; no cross-tenant access.
- **No Git credentials in QAssistant**: the push is performed entirely by the
  client; QAssistant only records a reference string supplied by the client.
- **Credential handling**: `authenticate` receives `email`/`password` from the
  client per session; tokens are held in memory for the server process lifetime
  and not persisted.
- **Untrusted content**: records returned to the client (DOM replay, screenshots,
  Jira text, generated code) remain untrusted input, consistent with existing
  codegen safety requirements.
- **Retention**: integration status/ref/error live on `generated_tests` and are
  removed with the existing session deletion lifecycle; no new retained data
  category is introduced.
